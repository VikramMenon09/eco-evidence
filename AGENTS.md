# EcoEvidence project work

EcoEvidence is a long-term, reproducible economics, environment, and business research toolkit. Prefer useful, verifiable capabilities over activity counts. Read README.md, docs/ROADMAP.md, and existing tests before choosing a contribution.

## Delivery

Use the fable-playbook in the lead session when available. Use real subagents for implementation or independent verification, with separate ownership boundaries. The lead integrates changes and exercises the normal CLI workflow. Cross-check each substantive change with the actual Claude CLI; identify the actual review scope and fix material findings. If the reviewer or a required check is unavailable, preserve a draft and report the blocker rather than claiming the work is ready.

A contribution is one coherent, substantial improvement: a sourced dataset adapter, a reproducible analysis or example, a useful research feature, or a meaningful reliability/accessibility fix. The portfolio routine targets three separately reviewed contributions per day across related projects; each session still needs a useful acceptance criterion. Do not split trivial work into PRs or fabricate data, contributors, reviews, stars, or answers.

## Evidence and data

Use primary sources and inspect the applicable terms before redistributing data. Keep original units, country and period coverage, dataset/indicator identity, retrieval timestamps, source URLs, and missing-value distinctions. Preserve raw responses or hashes sufficient to reproduce transformations. Explicitly label synthetic fixtures; never present them as observed data. Avoid causal or policy conclusions that the analysis cannot support.

## GitHub

Use a descriptive feature branch and focused pull request. A new project may begin with a license or project-charter bootstrap on main, followed by its first substantive code PR. Attribute actual work accurately. Run meaningful tests and a representative end-to-end CLI journey. Wait for CI on the current head before merging an authorized change. Preserve unrelated changes and existing review protections. No forced pushes to main, fabricated authorship, unsolicited review requests, paid services, or sponsorship transactions.

## Daily routine

See docs/DAILY_ROUTINE.md and docs/PORTFOLIO.md. Scheduling state is local and untracked. Only the native Codex Automations action may change the automation schedule. Do not edit automation configuration files directly or install system cron/launchd jobs. Preserve user pauses and later instructions. The clock is America/Los_Angeles; late or duplicate scheduler checks must not create extra GitHub activity. Explicitly requested manual work can proceed separately; do not record it as a scheduled session without a successful claim.
