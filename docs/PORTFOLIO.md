# Economics, environment and business portfolio

The owner requests more useful public contributions and new related projects. The routine targets **three focused contributions per Pacific day**, distributed across projects. Each contribution should deliver a usable feature, a reproduced and repaired defect, a sourced research example, or a meaningful reliability improvement. Passing reviews and checks determine publication; the target is not a guarantee that every attempt succeeds.

## New projects

Reserve one session each week for new-project development. Choose a distinct research or business question that does not fit an existing repository. An initial release needs a runnable vertical slice, honest source or assumption labels, installation/run instructions, meaningful tests, an explicit license, a roadmap and actual Claude review. Continue a promising unfinished prototype in later sessions instead of starting another shell repository.

New repositories belong to `VikramMenon09` and are public when intended for this portfolio. Before using a new repository in the scheduler, register its exact intended URL with `add-project` while no run is active. Check that an existing repository at that URL belongs to the intended work; a planned URL is not evidence that a repository has been created. The local allowlist does not grant access or create a repository. A license or project-charter bootstrap on main may precede the first substantive code PR. Keep later source-code and review changes in focused PRs, and verify CI on their actual heads before merging.

## Delivery standard

- Set one concrete acceptance criterion for each session. Keep changes substantial and reviewable; do not divide a single trivial edit into multiple commits or PRs to hit a number.
- Use the fable-playbook and real subagents with bounded ownership. The lead integrates and exercises the normal user workflow.
- Cross-check substantive work with the authenticated Claude CLI. Describe its actual review scope, fix material findings and retain the evidence.
- Preserve source units, provenance, original inputs, missingness and licensing. Hypothetical model inputs must stay explicitly hypothetical.
- Attribute AI assistance accurately. Use real commit times and the owner's verified commit identity. Do not fabricate collaborators, reviews, stars, issue answers or achievement awards.
- Publish only useful verified work, report the actual PR/repository and merge state, and retain blocked work with its specific reason. New paid services and sponsorship remain outside the routine.

The [schedule protocol](DAILY_ROUTINE.md) controls ownership, retries and timing. GitHub separately determines profile contribution credit: see its [official contribution criteria](https://docs.github.com/en/account-and-profile/reference/profile-contributions-reference). A local work log is not proof of a badge or a displayed graph count.
